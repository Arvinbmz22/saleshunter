# موتور جستجو و کشف (Search & Discovery Engine)

این سند معماریِ موتور جستجوی **AdminExt AI Lead Finder** را توضیح می‌دهد:
چندمرحله‌ای، چنددوره‌ای، تطبیقی، کیفیت‌محور و بدون هیچ اتوماسیون اینستاگرامی.

---

## ۱. اصول غیرقابل‌مذاکره

موتور جستجو هرگز:

- وارد اینستاگرام نمی‌شود، پسورد/کوکی/سشن ذخیره نمی‌کند
- دایرکت نمی‌فرستد، فالو/لایک/کامنت نمی‌کند
- کپچا، ضدربات یا محدودیت نرخ را دور نمی‌زند
- برای فرار از محدودیت از پروکسی استفاده نمی‌شود
- به حساب خصوصی یا اطلاعات غیرعمومی دسترسی پیدا نمی‌کند

فقط دادهٔ **عمومی** (نتایج موتور جستجو، وب‌سایت‌ها، فهرست‌های عمومی).
تماس با کسب‌وکار همیشه **دستی** است.

اگر فراهم‌کنندهٔ جستجو در دسترس نباشد:
**هیچ لید ساختگی ساخته نمی‌شود** و خطا با کد `SEARCH_PROVIDER_UNAVAILABLE`
به‌صورت شفاف برمی‌گردد.

## ۲. معماری کلی

```
درخواست کاربر (category, country, city, limit)
        ↓
نرمال‌سازی درخواست            lib/search/normalize.ts
        ↓
درک صنف (لایه‌های واژگان)     lib/search/categoryProfile.ts
        ↓
درک موقعیت (شهر/کشور/لاتین)   lib/search/normalize.ts + categoryProfile
        ↓
تولید خانواده‌های کوئری        lib/search/queryPlan.ts
        ↓
امتیازدهی + رتبه‌بندی + تنوع   rankQueries / diversify / dedupePlan
        ↓
برنامه‌ریزی دورها              planRounds ( round 1..N )
        ↓
┌─────────────── SearchEngine (lib/search/engine.ts) ───────────────┐
│  for round in rounds:                                             │
│     انتخاب کوئری (زمان‌بندی + بهره‌برداری + اکتشاف + تطبیقی)        │
│     اجرا با SearchProvider (timeout/خطا/partial)                  │
│     نرمال‌سازی و کانونیکال‌سازی URL                                │
│     دِدوپ نتایج (درون جلسه)                                        │
│     استخراج و ادغام کاندیداها      lib/search/discovery.ts        │
│     دِدوپ تاریخی (data/leads.json)                                 │
│     فیلتر ارزان (سیگنال‌های cheap) lib/search/signals.ts           │
│     اندازه‌گیری عملکرد کوئری/خانواده                               │
│     تشخیص الگوی شکست → کوئری تطبیقی                                │
│     بررسی شرط توقف                                                │
└───────────────────────────────────────────────────────────────────┘
        ↓
استخر کاندیداها (مرتب‌شده بر اساس promise score)
        ↓
احراز (ایران / کسب‌وکار / فروش آنلاین / فعالیت)   lib/verification/*
        ↓
AI اختیاری → امتیاز → رتبه‌بندی → فقط لیدهای NEW
```

مرز مشخص است:
**جستجو فقط کاندیدا پیدا می‌کند؛ احراز تصمیم می‌گیرد که کاندیدا واقعی هست یا نه.**
هیچ سیگنال ارزانِ جستجویی به‌تنهایی باعث رد قطعی یک کسب‌وکار نمی‌شود.

## ۳. ماژول‌ها

| فایل | مسئولیت |
| --- | --- |
| `lib/search/normalize.ts` | نرمال‌سازی متن/درخواست (ي→ی، ك→ک، نیم‌فاصله، نویسه‌های کنترلی)، کانونیکال‌سازی URL، کلید کوئری، شباهت کوئری |
| `lib/search/categoryProfile.ts` | واژگان لایه‌ای هر صنف: مترادف، واژگان کسب‌وکار، محصول/زیردسته، واژگان تجاری، واژگان منفی (جایگزین `synonyms.ts` قدیمی) |
| `lib/search/queryPlan.ts` | خانواده‌های کوئری، امتیاز/رتبه/تنوع، زمان‌بندی دورها، کوئری‌های تطبیقی و پیگیری (follow-up) |
| `lib/search/provider.ts` | انتزاع `SearchProvider` + قابلیت‌ها، timeout، دسته‌بندی خطا، mock برچسب‌خورده |
| `lib/search/execute.ts` | اجرای یک کوئری با ثبت آمار و تحمل خطا (بدون کرش کردن کل جستجو) |
| `lib/search/discovery.ts` | استخراج کاندیدا، هویت کانونیکال، ادغام درون‌جلسه‌ای و سطح‌کسب‌وکار، منبع‌یابی |
| `lib/search/signals.ts` | سیگنال‌های ارزان (مثبت/منفی)، فیلتر اولیه، امتیاز promise برای مرتب‌سازی |
| `lib/search/engine.ts` | موتور چنددوره‌ای: بودجه، آمار، تطبیق، شرط توقف، تشخیص‌پذیری |
| `types/search.ts` | انواع `SearchQuery`, `QueryStats`, `SearchState`, `SearchDiagnostics`, `Candidate` |

## ۴. خانواده‌های کوئری

هر خانواده هدف متفاوتی دارد؛ هیچ قالب واحدِ غول‌آسا وجود ندارد.

| خانواده | هدف | نمونه |
| --- | --- | --- |
| `exact_category` | انطباق مستقیم صنف | `site:instagram.com "لوازم آرایشی" تهران` |
| `commercial_intent` | پیدا کردن کسب‌وکار نه صفحهٔ محتوا | `site:instagram.com "فروش لوازم آرایشی" تهران` |
| `business_type` | نوع کسب‌وکار | `"فروشگاه اینترنتی لوازم آرایشی" تهران` |
| `contact_channel` | کانال سفارش/پشتیبانی | `site:instagram.com "سفارش از دایرکت" لوازم آرایشی تهران` |
| `product_specific` | کسب‌وکارهایی که صنف را در پروفایل ندارند | `"ضدآفتاب" تهران فروشگاه` |
| `website` | کشف خارج از اینستاگرام | `"لوازم آرایشی" تهران سایت` |
| `domain` | سیگنال دامنهٔ محلی | `site:.ir "لوازم آرایشی" تهران` |
| `directory` | فهرست‌های عمومی کسب‌وکار | `"لوازم آرایشی" "تهران" "آدرس"` |
| `location_focus` | تمرکز شهری (آدرس/تلفن/تومان) | `"لوازم آرایشی" تهران آدرس` |
| `follow_up` | پیدا کردن سایت/هویت برای کاندیداهای ضعیف | `"niloofar_cosmetics" تهران` |
| `adaptive` | تولیدشده بر اساس الگوی شکست | بسته به الگو |

### تنوع و عدم تکرار

- شباهت کوئری با **Jaccard روی مجموعهٔ توکن‌ها** سنجیده می‌شود.
- کوئری‌هایی که مجموعهٔ توکن یکسان دارند (فقط تفاوت در نقل‌قول یا ترتیب)
  در سراسر خانواده‌ها حذف می‌شوند و کوئری با اولویت بالاتر می‌ماند (§۱۴).
- هر کوئریِ نرمال‌شده فقط **یک بار** در هر جلسه اجرا می‌شود (§۹۲).

### فرمول اولویت (ساده و قابل توضیح)

```
priority = 100 × (
    0.30 × expectedValue
  + 0.22 × commercialIntent
  + 0.18 × locationSpecificity
  + 0.15 × categoryRelevance
  + 0.15 × diversityScore
)
```

## ۵. قابلیت‌های فراهم‌کننده (هیچ منطق provider در هسته)

```ts
type ProviderCapabilities = {
  siteOperator: boolean       // آیا site: پشتیبانی می‌شود؟
  negativeTerms: boolean      // آیا واژگان منفی (-خبر) پشتیبانی می‌شود؟
  maxResultsPerQuery: number
}
```

| Provider | `site:` | واژگان منفی |
| --- | --- | --- |
| Serper (Google) | بله | بله |
| Brave | بله | بله |
| Tavily | خیر | خیر |
| Mock | بله | بله |

اگر فراهم‌کننده `site:` را پشتیبانی نکند، برنامه‌ساز به‌جای
`site:instagram.com …` از `instagram.com …` استفاده می‌کند و خانوادهٔ
`domain` را کلاً حذف می‌کند — نه اینکه کوئری بی‌فایده بفرستد.

## ۶. دورها و بودجه

دورها (تعداد واقعی تطبیقی است، سقف پیش‌فرض ۷ دور):

| دور | تمرکز |
| --- | --- |
| ۱ | کشف گسترده: صنف دقیق + نیت تجاری + نوع کسب‌وکار + موقعیت |
| ۲ | نیت تجاری + کانال سفارش |
| ۳ | تمرکز شهر/کشور + فهرست‌ها |
| ۴ | محصول/زیردسته + وب‌سایت |
| ۵ | وب‌سایت + دامنه + فهرست |
| ۶ | **تطبیقی** بر اساس الگوهای شکست مشاهده‌شده |
| ۷ | کانال تماس + پیگیری (follow-up) کاندیداهای ضعیف |

در هر دور (بعد از دور ۱) علاوه بر کوئری‌های زمان‌بندی‌شده:

- **بهره‌برداری**: تا چند کوئری از خانواده‌هایی که بیشترین بازدهی را داشته‌اند
- **حداقل اکتشاف**: همیشه یک کوئری از کم‌استفاده‌ترین خانواده (جلوگیری از سوگیری)

### بودجه (قابل تنظیم با env)

| متغیر | پیش‌فرض | معنا |
| --- | --- | --- |
| `SEARCH_BUDGET` | ۸۰ | سقف تعداد کوئری |
| `SEARCH_MAX_ROUNDS` | ۷ | سقف دورها |
| `SEARCH_MAX_CANDIDATES` | `max(120, limit×15)` | سقف کاندیداها |
| `SEARCH_MAX_TIME_MS` | ۱۲۰۰۰۰ | سقف زمان کل |
| `SEARCH_RESULTS_PER_QUERY` | ۱۰ | سقف نتایج هر کوئری |
| `SEARCH_TIMEOUT_MS` | ۱۲۰۰۰ | timeout هر فراخوان |

عمق جستجو بر اساس **سختی صنف** تطبیقی است
(`EASY / MEDIUM / HARD / VERY_HARD` بر اساس کاندیدا به‌ازای کوئری).
هیچ ضریب ثابتی مثل «درخواست × ۵» در کد سخت نشده است.

## ۷. کانونیکال‌سازی URL و هویت

چهار آدرس زیر یک پروفایل‌اند:

```
https://instagram.com/shop
https://instagram.com/shop/
https://www.instagram.com/shop
https://www.instagram.com/shop/?utm_source=x
```

کانونیکال‌سازی: حذف `www.`، قطعه (`#`)، پارامترهای ردیابی
(`utm_*`, `fbclid`, `igshid`, …)، اسلش انتهایی و مرتب‌سازی پارامترها.
مسیرهای غیرپروفایل اینستاگرام (`/p/`, `/reel/`, `/explore/`) پروفایل محسوب نمی‌شوند.

هویت کاندیدا به‌ترتیب اولویت:

1. یوزرنیم نرمال‌شدهٔ اینستاگرام
2. هاست کانونیکال وب‌سایت
3. نام کسب‌وکار + شهر

ادغامِ سطح‌کسب‌وکار فقط با **شواهند معنادار** انجام می‌شود
(وب‌سایت یکسان **و** نام یکسان)، نه شباهت ضعیف.

## ۸. دِدوپ

| سطح | قانون |
| --- | --- |
| نتایج | کلید URL کانونیکال در کل جلسه |
| درون جلسه | هویت کاندیدا؛ شواهد و کوئری‌ها ادغام می‌شوند (۱ کاندیدا نه ۳) |
| تاریخی | مقایسه با `data/leads.json` **قبل از** احراز گران‌قیمت |
| ذخیره‌سازی | `addLead` باز هم بر اساس یوزرنیم/وب‌سایت/نام+شهر چک می‌کند |

لیدهای تاریخی حذف نمی‌شوند؛ برای اندازه‌گیری اشباع کوئری‌ها استفاده می‌شوند،
اما دیگر به‌عنوان لید جدید نمایش داده نمی‌شوند.

## ۹. الشرط توقف

| دلیل توقف | معنا |
| --- | --- |
| `ENOUGH_QUALIFIED_LEADS` | تعداد لید باکیفیتِ درخواستی به دست آمد |
| `SEARCH_BUDGET_EXHAUSTED` | سقف کوئری یا کاندیدا تمام شد |
| `DIMINISHING_RETURNS` | دو دور پیاپی تقریباً کاندیدای تازه‌ای نداشتند |
| `NO_MORE_USEFUL_RESULTS` | کوئری مفید دیگری باقی نمانده |
| `MAX_ROUNDS` | سقف دورها انجام شد |
| `TIME_BUDGET_EXHAUSTED` | زمان جستجو به پایان رسید |
| `PROVIDER_LIMIT` | فراهم‌کننده محدودیت نرخ اعمال کرد (بدون دور زدن) |
| `PROVIDER_FAILURE` | خطای فراهم‌کننده (بدون ساخت نتیجهٔ جعلی) |
| `NO_RESULTS` | هیچ نتیجه‌ای از منابع عمومی به دست نیامد |

همیشه دلیل توقف ثبت و در UI نمایش داده می‌شود.

## ۱۰. رفتار در برابر خطای فراهم‌کننده

- هر فراخوان timeout دارد؛ یک کوئریِ شکست‌خورده کل جستجو را نمی‌کشد.
- خطاها دسته‌بندی می‌شوند: `timeout | rate_limited | network | http | malformed`.
- **محدودیت نرخ تلاشِ مجدد نمی‌شود** و با `PROVIDER_LIMIT` جستجو متوقف می‌شود.
- نتایجِ موفقِ قبلی حفظ می‌شوند و `partialSearch = true` ثبت می‌شود.
- پیام خطا قبل از رسیدن به UI از کلیدها/توکن‌ها پاک‌سازی می‌شود.

## ۱۱. تشخیص‌پذیری (Observability)

هر جستجو این‌ها را گزارش می‌کند:

- تعداد کوئری تولیدشده / اجراشده / ناموفق
- نتایج خام و یکتا، تعداد کاندیداها
- تکراری تاریخی، تکراری درون‌جلسه‌ای، رد first-stage
- تعداد دورها و **دلیل توقف**
- سختی صنف، الگوهای ضعف نتایج، خطاهای فراهم‌کننده
- آمار هر خانوادهٔ کوئری (کاندیدا/کوئری، ارزش نسبی)

UI این گزارش را در «گزارش موتور جستجو» نشان می‌دهد و صریحاً می‌گوید
اینترنت «به‌طور کامل» جستجو نشده است.

## ۱۳. محدودیت‌های باقی‌مانده (صادقانه)

- جستجوی واقعی نیازمند کلید است (`TAVILY_API_KEY` / `SERPER_API_KEY` / `BRAVE_API_KEY`)؛
  بدون آن فقط mock برچسب‌خورده اجرا می‌شود.
- موتور فقط منابع و کوئری‌هایی را می‌شناسد که برایش تعریف شده؛
  ادعای «جستجوی کل اینترنت» وجود ندارد.
- واژگان صنف برای ۹ دسته تعریف شده (لوازم آرایشی، پوشاک، طلا، الکترونیک،
  خانه، رستوران، خدمات/کلینیک، آموزش، خودرو)؛ بقیه از پروفایل عمومی استفاده می‌کنند.
- امتیاز promise برای **مرتب‌سازی** است، نه تصمیم نهایی.
- کش حافظه‌ای برای نتایج در MVP فعال نیست؛ هر جلسه از نو جستجو می‌کند
  (به‌جز دِدوپ درون‌جلسه‌ای و تاریخی).
